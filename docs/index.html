Comment j'ai construit Vigie

Un mini SIEM en Python, par Chahé Papazian

Vigie lit des fichiers de logs (Linux, Windows, serveur web, pare-feu) et cherche dedans les traces d'une attaque : quelqu'un qui teste des mots de passe en boucle, une injection SQL, un compte admin créé le soir, un journal effacé. Quand plusieurs alertes viennent de la même attaque, il les regroupe en un incident.

Pendant mon alternance chez Anetys, j'ai utilisé ELK pour surveiller le réseau. Je voyais les alertes, mais je ne savais pas vraiment comment elles étaient produites. Coder un petit SIEM moi-même m'a semblé le meilleur moyen de comprendre. Cette page explique comment il est fait.

1. Lire les logs

Chaque type de log a son format. Une ligne de auth.log ressemble à ça :

Oct 28 21:10:00 web01 sshd[14303]: Failed password for root from 203.0.113.45 port 42614 ssh2

Il y a un parser par source (SSH et sudo, pare-feu UFW, accès web Apache/Nginx, événements Windows exportés en JSON). Chacun transforme une ligne en un objet Event, avec les mêmes champs pour tout le monde :

ts: 2026-10-28 21:10:00    source: linux       action: auth_failure
host: web01                user: root          src_ip: 203.0.113.45
origin: auth.log:233

C'est le choix le plus utile du projet. Une fois les logs ramenés au même format, une règle comme « des échecs puis une connexion qui réussit » marche aussi bien sur du SSH que sur des connexions Windows. Et le champ origin permet de retrouver la ligne de départ, ce qui sert de preuve dans le rapport.

Les dates demandent de l'attention. Syslog n'écrit pas l'année, et les événements Windows peuvent être exportés en UTC alors que les logs Linux sont en heure locale : en les mélangeant tels quels, on se retrouve avec une heure d'écart. D'où les options --year et --tz, qui ramènent tout dans le même fuseau avant de comparer. Côté Windows, le JSON de PowerShell peut aussi commencer par un BOM que json.loads refuse, et le format des dates change selon la version de PowerShell.

2. Écrire les règles

Je voulais pouvoir ajouter une détection sans toucher au code, donc les règles sont des fichiers YAML (un peu dans l'esprit de Sigma). La force brute SSH :

id: VIG-001
title: Force brute SSH
severity: high
mitre: [T1110.001]
match:
  source: linux
  action: auth_failure
threshold:
  group_by: src_ip
  count: 8
  window: 5m
message: "{count} échecs de connexion SSH depuis {src_ip} en {duration}"

Il y a trois sortes de règles :

  • simple : un seul événement suffit, par exemple un journal de sécurité Windows effacé ;
  • seuil : X événements dans une fenêtre de temps (8 échecs en 5 minutes), ou X valeurs différentes (5 comptes différents essayés depuis la même IP, c'est du password spraying) ;
  • séquence : une étape puis une autre pour la même IP, par exemple au moins 5 échecs puis une connexion réussie dans la demi-heure.

Chaque règle indique la technique MITRE ATT&CK qu'elle couvre. Il y en a 15 en tout, du scan de ports jusqu'à l'effacement des traces. La liste complète est dans le README.

3. Le moteur

Le moteur passe les événements dans l'ordre chronologique. Pour les seuils, il garde une fenêtre glissante par IP (ou par compte). Pour les séquences, il retient l'étape où en est chaque IP et repart de zéro si la suite arrive trop tard.

Si on lève une alerte à chaque fois que le seuil est dépassé, une force brute de 30 essais donne une vingtaine d'alertes identiques. Donc tant que l'attaque continue, c'est la même alerte qui se met à jour (nombre d'événements, durée, preuves). Pareil pour un scanner web qui envoie des centaines de requêtes.

4. Regrouper en incidents

Dix alertes séparées, c'est encore difficile à lire. Vigie les regroupe comme je le ferais à la main : même IP source, même compte (si l'attaquant se connecte avec deploy puis crée backup2, les deux comptes sont liés), ou à défaut même machine dans la demi-heure. Ça donne une chronologie par attaque.

5. Tester sans vraies attaques

Je n'avais pas de vrais logs d'attaque, alors j'ai écrit un script (samples/generate.py) qui génère une journée de logs pour une petite entreprise : un serveur web, un pare-feu, un contrôleur de domaine. Il y a environ 1 900 événements normaux (connexions, fautes de frappe, trafic web, bots d'Internet) et deux attaques glissées dedans. Les IP des attaquants viennent des plages réservées à la documentation.

La première attaque (203.0.113.45) :

  1. scan de ports sur le pare-feu ;
  2. Nikto puis sqlmap sur le site, un essai de XSS et de lecture de /etc/passwd ;
  3. force brute SSH, puis connexion réussie avec le compte deploy ;
  4. shell root avec sudo, création d'un compte backup2 ajouté au groupe sudo.

La deuxième (198.51.100.23) :

  1. password spraying lent sur dix comptes, puis des essais en rafale sur administrateur ;
  2. connexion sur le contrôleur de domaine avec jdupont ;
  3. PowerShell encodé, création d'un compte admin, installation d'un service depuis C:\Users\Public ;
  4. effacement du journal de sécurité.

Le générateur écrit aussi la liste des 18 alertes attendues. Le test principal lance Vigie sur ces logs et vérifie que les 18 sont trouvées et qu'il n'y en a aucune autre. C'est aussi lui qui sert à régler les seuils : trop bas, une personne qui se trompe deux fois de mot de passe déclencherait une alerte ; trop haut, le password spraying passerait inaperçu. La CI GitHub Actions relance tous les tests à chaque push.

git clone https://github.com/ChaheEnNSI/vigie
cd vigie
pip install -e .
python -m vigie scan samples --year 2026 --tz Europe/Paris

6. Le rapport

En plus de la sortie dans le terminal, Vigie peut produire un JSON ou une page HTML avec les incidents, la chronologie et les lignes de logs en preuve. Le rapport affiche des URL et des user-agents écrits par l'attaquant, donc il fallait faire attention : sans échappement, un <script> glissé dans une requête s'exécuterait dans le navigateur de la personne qui lit le rapport. Tout est échappé, la page interdit les scripts, et un test vérifie le cas.

Où j'en suis

Sur les logs de démo, les deux attaques sont reconstituées sans fausse alerte. Mais ces logs, c'est moi qui les ai générés, et les seuils sont réglés pour eux. Sur de vrais logs, il faudrait les ajuster.

Ce que je veux faire ensuite :

  • un mode --follow pour lire les logs en direct au lieu de fichiers ;
  • importer des règles Sigma plutôt que de tout réécrire ;
  • lire les logs Sysmon ;
  • monter un petit labo Docker pour rejouer de vraies attaques et voir ce que Vigie rate.
