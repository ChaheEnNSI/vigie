Vigie

Un petit SIEM écrit en Python. Il lit les journaux d’un système (Linux, Windows, serveur web, pare-feu), repère les attaques avec des règles reliées à MITRE ATT&CK, puis reconstitue chaque incident dans l’ordre, comme le ferait un analyste de SOC.

01 · Le problèmeLes traces sont là. Personne ne les lit.

Un serveur écrit des milliers de lignes de journaux par jour. Une attaque y laisse presque toujours des traces : des échecs de connexion en rafale, une requête web étrange, un compte créé tard le soir, un journal effacé.

Le problème n’est pas de collecter ces traces, c’est de les trier : repérer les quelques lignes qui comptent, et comprendre qu’elles racontent la même histoire. C’est le travail d’un SIEM, et celui d’un analyste de SOC. Vigie en reproduit l’essentiel, en petit, avec un code que l’on peut lire en entier.

02 · Le fonctionnementDu fichier brut à l’incident.

  1. Lecture

    Chaque ligne est reconnue toute seule : syslog SSH et sudo, pare-feu UFW, accès web, événements Windows en JSON.

  2. Normalisation

    Tout devient un événement au même format : heure, source, action, compte, adresse.

  3. Règles

    Des fichiers YAML lisibles : un événement suffit, un seuil dans une fenêtre de temps, ou une séquence.

  4. Corrélation

    Les alertes liées (même adresse, même compte, même machine) forment un incident.

  5. Rapport

    Dans le terminal, en JSON pour un autre outil, ou en page HTML autonome.

Une règle, c’est quelques lignes

Pas besoin de toucher au code pour ajouter une détection. La force brute SSH, par exemple :

id: VIG-001
title: Force brute SSH
severity: high
mitre: [T1110.001]
match:
  source: linux
  action: auth_failure
threshold:
  group_by: src_ip
  count: 8
  window: 5m
message: "{count} échecs SSH depuis {src_ip} en {duration}"

Trois types de règles

Simple : un seul événement suffit. Un journal de sécurité effacé, par exemple.

Seuil : N événements, ou N valeurs différentes, dans une fenêtre glissante. Huit échecs en cinq minutes, ou cinq comptes différents essayés depuis la même adresse.

Séquence : une étape, puis une autre, pour la même adresse. Des échecs de connexion… suivis d’une connexion réussie : le mot de passe est probablement tombé.

Une attaque qui dure produit une alerte qui grossit, pas cent : l’analyste n’est pas noyé.

Ces chiffres ne sont pas écrits à la main : un test les vérifie à chaque modification du code, et l’intégration continue (GitHub Actions) relance toute la suite sur trois versions de Python.

À garder en tête : ces journaux sont simulés et l’attaque est connue d’avance. Sur un vrai système, il faut ajuster les seuils à l’activité normale. Un bon réglage compte autant que la règle elle-même.

06 · Les choix techniquesCe qui a été pensé, et pourquoi.

Un format commun pour tout

Linux, Windows, web et pare-feu deviennent le même objet Event. Une règle peut donc viser plusieurs sources à la fois : la pulvérisation de mots de passe est vue sur SSH et sur Windows.

Rien ne se perd en silence

Une ligne non reconnue est comptée et signalée. Un fichier JSON invalide n’arrête pas l’analyse des autres.

Un rapport qui ne s’exécute pas

Les journaux contiennent ce que les attaquants y écrivent, y compris du HTML piégé. Tout est échappé, et le rapport interdit tout script (CSP). Un test vérifie qu’un <script> glissé dans une URL reste du texte.

Des règles chargées sans risque

Les fichiers YAML sont lus avec safe_load : impossible d’y glisser du code Python. Une règle mal écrite est refusée avec un message clair.

Des heures comparables

Syslog n’indique ni l’année ni le fuseau, Windows écrit en heure UTC ou locale. Tout est ramené dans un même fuseau avant de comparer.

Des données de test reproductibles

Le générateur de journaux utilise une graine fixe : la CI vérifie que les fichiers du dépôt sont exactement ceux qu’il produit.
